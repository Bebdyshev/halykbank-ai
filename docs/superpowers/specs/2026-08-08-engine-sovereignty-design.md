# Суверенитет движка + ремонт знаменателя (пред-сдаточная стабилизация)

Дата: 2026-08-08 (день до 3-часового окна сдачи). Одобрено: A+B.

## Проблема

Холодная репетиция пакета A: 32.4/36 против 34.5 у тёплого прогона той же
конфигурации. Вся разница — дисперсия двух ячеек (P7/P9 6.1), качающая ±2.0
балла на единственном боевом прогоне. Замеренный механизм (9 замеров GT, все
объявлены):

- **Класс P9**: движок до судьи выдаёт ТОЧНЫЙ ответ (BREACH 0.22 = GT);
  вмешательства судьи (перемаркировки/перечтения → пересчёт) портят его
  (COMPLIANT 0.08). Статус-перевороты посчитанных ячеек судьёй/решателем:
  **6 из 6 неверны** (P2, P5, P7 итер-5; B1 6.2 прогон-3; P9, P2-actual холод).
- **Класс P7**: извлечение читает «операционные расходы» широко (7 категорий)
  → знаменатель EBITDA-отношения отрицательный (−4.87M) → страж
  NegativeDenominator корректно отказывается считать → ячейка пуста → вольный
  решатель заполняет наугад (COMPLIANT 0.01 vs GT BREACH 0.36). Страж работает,
  пути РЕМОНТА нет.

## Решение

### A. Замок статусов (judge.py, ~12 строк)

После всех раундов судьи, перед записью `answers_judged.json`:

- Для каждой ячейки, посчитанной движком до судьи (`answers_before`):
  финальный ответ обязан совпасть с движковым (status, actual, evidence).
  Расхождение → восстановить `answers_before[sid][clause]` целиком, флаг
  `judge_flip_reverted` в отчёт.
- Исключение: движковый `evidence_txn_id is None` и финальный валиден →
  принять финальный evidence (добавление, не порча).
- Ячейки, пустые до судьи, — как сейчас (ремонт спека / решатель).
- Судья сохраняет ценность: чинит пустые ячейки; его правки категорий влияют
  на будущие прогоны через persisted facts, но не на посчитанные ячейки этого.

Обоснование: движок на посчитанных ячейках не ошибся ни разу за все замеры;
вмешательства — 6/6 неверны. Замок фиксирует эмпирически сильнейший источник.

### B1. Ремонт отрицательного знаменателя (run_all.py, ~20 строк, без промптов)

При `NegativeDenominator` на клаузе с формулой вида `X / (A − B)`:

- если категории компонента B — широкий набор ⊇ {OPEX} с дополнительными
  категориями: пересобрать ковенант с B, суженным до `["OPEX"]`, пересчитать;
- посчиталось с положительным знаменателем → принять результат + флаг
  `denominator_narrowed_to_opex`;
- иначе ячейка остаётся пустой (путь решателя).

Обоснование: таксономия уже выделяет PAYROLL/INSURANCE/RENT_LEASE/… отдельными
категориями, поэтому «Операционные расходы» договора = узкий OPEX. Подтверждено
P7 (B6-движок с OPEX-only дал верный BREACH 0.359) и направлением судейских
перемаркировок P6. Применяется ТОЛЬКО когда иначе ячейка пуста — хуже сделать
не может.

### B2. Усиление решателя для всё ещё пустых ячеек (judge.py)

- Сэмплов голосования 3 → 5 (большинство по статусу, медиана actual).
- В промпт решателя добавляется таблица готовых сумм по категориям
  (детерминированно посчитанных движком): LLM выбирает состав формулы, но не
  делает свободную арифметику. Инвалидирует только кэш решателя.

## Валидация (сегодня)

1. Тёплый прогон (кэш свеж после холодной репетиции; живьём — решатель и
   пересчёты, ~$0.5–1).
2. Дифф против холодного прогона. Ожидание: P9 6.1 → BREACH 0.22 (замок),
   P2 6.1 → 1.18 (замок), P7 6.1 → BREACH ≈0.36 (ремонт знаменателя).
3. Один объявленный замер GT. Критерий заморозки: ≥ 33 и ноль новых регрессий
   против холодного.
4. RUNBOOK: тайминг холодного прогона 1ч47м (не 44м); два прогона в окно не
   влезают — план Б только через перезапуск из кэша; чек баланса ≥ $5.

## Вне скоупа (осознанно)

- Температурная детерминизация всех стадий (глобальный риск, не валидировать
  за день).
- P4 6.1/6.3 (документально трудные, стабильны между прогонами).
- Любые изменения промптов извлечения/классификации (кэш-дисциплина дня Х).

## Риски

- Замок закрепит неверный движковый ответ, если движок ошибётся на посчитанной
  ячейке: за 9 замеров таких случаев ноль; принято.
- Сужение до OPEX — эвристика одного датасета: применяется только к иначе
  пустым ячейкам; в худшем случае эквивалентна текущему поведению (пустая →
  решатель).
