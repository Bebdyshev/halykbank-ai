# Дизайн: аудитор-специфичный состав ковенантных компонентов

Дата: 2026-08-07. Цель: конкурс (скрытый датасет того же генератора).
Бейзлайн: 32.2/36 вслепую. Ожидание: +1.5–3 балла. Бюджет: ~$1 DeepSeek.

## Проблема

Договоры займа шаблонны и парсятся надёжно. Финансовые примечания делают 5 разных
аудиторских фирм, и **состав** «Выручки» и «Операционных расходов» определяется
аудитором по-разному. Пайплайн же считает компоненты формул по фиксированным
категориям (REVENUE, OPEX) — нашей собственной договорённости. Все текущие потери
типа 6.1 (P3, P4, P7) — это расхождение состава EBITDA/выручки между нашей
раскладкой и версией конкретного аудитора; судья это видит, но чинит вслепую.

## Решение (3 механизма, работают связкой)

### 1. Карта состава (composition map) — основной механизм
Новый модуль `src/composition.py`. Один вызов v4-pro на заёмщика:
вход — цитаты пунктов договора + ПОЛНЫЙ текст примечаний его аудитора +
леджер с нашими категориями; выход — для каждого компонента каждой формулы
**явный список txn_id**, входящих в компонент по версии этого аудитора,
с цитатой-обоснованием из примечаний.

Схема: `{clauses: [{clause, components: [{name, txn_ids: [...],
includes_off_ledger: [...], basis_quote}]}]}`.

`compute.py`: спека компонента получает опциональный селектор `txn_ids` —
если он есть, компонент суммирует явно перечисленные строки (после всех
корректировок: fills/reclass/exclusions/FX), игнорируя категории. Категории
остаются для компонентов без карты и для остального пайплайна.

`run_all.py`: если карта покрывает компонент — подменяет его определение;
расхождение карты с категорийной суммой >1% — флаг `composition_divergence`
(информационный, в judge-контекст).

### 2. Сверка с заявленными итогами — детерминированный валидатор
`AUDIT_SCHEMA` + поле `stated_figures: [{metric_name, amount_usd, quote}]` —
все итоговые суммы, которые аудитор называет явно (выручка за период,
операционные расходы, EBITDA и т.п.).

Код (не LLM) проверяет: сумма компонента по карте == заявленная цифра
(допуск $0.01). Несовпадение → один ремонтный вызов composition с указанием
целевого числа («аудитор утверждает X, твой состав даёт Y — пересмотри»);
после ремонта осталось несовпадение → флаг `stated_figure_mismatch` судье.
Генератор сводит числа точно, поэтому проверка «до цента» — сильный сигнал.

### 3. H5: few-shot валидной формулы
В `COVENANT_PROMPT` — один образец корректного clause-объекта (формула,
компоненты, порог). Чинит битые формулы DeepSeek на P4 (json_object-режим
без строгих схем). Побочный эффект: смена промпта инвалидирует кэш ковенантов
→ свежее переизвлечение всех 12 договоров (это желаемо: P4/P7 формулы).

## Поток данных

extract (аудит + stated_figures, ковенанты с few-shot) → categorize (без
изменений, из кэша) → **composition (новый)** → reconcile (код) →
run_all (карта подменяет компоненты) → judge (получает карту, цитаты,
результат сверки; новый тип issue `composition_mismatch`).

## Ошибки и деградация

- Карта не покрыла компонент → категорийное поведение как сейчас (не хуже).
- Ремонт не сошёлся со stated figure → флаг судье, ячейка живёт с картой.
- txn_id из карты нет в леджере → игнор + флаг.

## Тесты

- unit: компонент с `txn_ids` суммирует явные строки; корректировки
  (fill/reclass/exclusion/FX) применяются к явным строкам так же.
- unit: сверка ловит несовпадение и зовёт ремонт один раз.
- Финальная проверка — слепой прогон + ЕДИНСТВЕННЫЙ замер по GT (№5, с отчётом).

## Не делаем

Фирменные адаптеры (вариант 3 брейншторма) — паттерн-подгонка. Изменения
categorize.py — не нужны, карта работает поверх.
